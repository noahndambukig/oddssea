## 00:17 — finding — Review of C's plan exposed a B gap: revocation was enabled but never invoked

**What happened:** Round 13 of the Codex review on the Increment C plan
flagged that "sign out → 401" only proves the browser stopped *sending*
credentials. Checking the claim against the shipped Increment B code made
it sharper than the reviewer knew: `infra/lib/constructs/auth.ts` sets
`enableTokenRevocation: true` with the comment "lets logout actually
invalidate the refresh token server-side" — and `logout()` in
`web/src/auth/auth-client.ts` never calls the revocation endpoint. The
capability was built, documented in a comment, and never collected on. The
one-day refresh token — the longest-lived credential in the system —
outlived every sign-out.

Fixed in the C build: logout is now three things (drop local tokens,
best-effort `POST /oauth2/revoke` with `keepalive` so the request survives
the redirect it races, end the Cognito session). What revocation cannot
do is also now stated honestly in the walkthrough: the API's JWT
authorizer verifies offline against cached public keys and never asks
Cognito whether a token is still good, so outstanding access tokens stay
accepted until their ≤1h expiry regardless.

**Why it matters:** Two lessons. First, a comment describing intent is not
the intent — the flag and its caller shipped in the same increment, in
different workspaces, and nothing connected them; only an adversarial pass
that asked "who calls this?" found the gap. Second, the ≤1h acceptance
window is not a bug to fix but the defining trade of stateless
verification — revocation immediacy exchanged for zero-latency auth —
and the honest response is to teach it and pin where it gets revisited
(`docs/decisions/0017`'s BFF gate, before money exists).

**Refs:** `web/src/auth/auth-client.ts` (logout), `infra/README.md`
Part 7 concepts, `.review/replicated-watching-truffle/ledger.md` rounds
10–13

## 01:15 — finding — A review finding was wrong, and only the deployed API could say so

**What happened:** Increment C deployed cleanly (307s; the ordering held —
routes at 12:56:44, cert/domain/mapping/record through 12:59:28, and the
site upload only then, 12:59:29 → 1:01:09, exactly what `api.ready` is
for). Then the first curl against the live API contradicted a plan claim
that had survived a review round and a documentation check.

Codex round 12 asserted that authorizer-generated 401/403 responses carry
no CORS headers, so browser JS would see `TypeError: Failed to fetch`
rather than a status. AWS's own wording supported it — CORS headers are
added "to the response from an integration", and a rejected request never
reaches one. I verified that sentence in the docs, agreed, and rebuilt the
API panel around rendering the block as the demonstration, moving the
numeric checks to curl.

Measured against the deployed API, it is false:

```
$ curl -i https://api.oddssea.xyz/me -H "Origin: https://oddssea.xyz"
HTTP/1.1 401 Unauthorized
access-control-allow-origin: https://oddssea.xyz
```

Correctly absent for an origin outside the allow-list, present for one
inside it. Confirmed in a browser: the panel renders a real `401`. The
advice is genuine but belongs to **REST APIs (v1)**, where gateway
responses need CORS wired by hand; **HTTP APIs (v2)** do it themselves.
Reverted in code and docs; the panel now renders 401/403 with teaching
notes and reserves its catch branch for real network failures.

Also observed, and now taught: signed out, `/me` sends **no** preflight —
there is no `Authorization` header to trigger one. The `OPTIONS` appears
only when signed in. The rule made visible.

**Why it matters:** This is the 2026-08-04 21:15 lesson recurring one
level up. There, a passing typecheck and build did not prove the program
ran. Here, an adversarial reviewer *and* a documentation lookup did not
prove the claim true — a sentence about one case (integration responses)
was read as a statement about another (gateway responses), and the
version distinction that governs it went unnoticed. Both defences were
the strongest available short of running it, and running it took one
curl. **Verify AWS behaviour against the deployed thing, and check which
API generation any advice was written for.**
