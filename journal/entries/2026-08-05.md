# 2026-08-05

## 00:17 — finding — Review of C's plan exposed a B gap: revocation was enabled but never invoked

**What happened:** Round 13 of the Codex review on the Increment C plan
flagged that "sign out → 401" only proves the browser stopped *sending*
credentials. Checking the claim against the shipped Increment B code made
it sharper than the reviewer knew: `infra/lib/constructs/auth.ts` sets
`enableTokenRevocation: true` with the comment "lets logout actually
invalidate the refresh token server-side" — and `logout()` in
`web/src/auth/auth-client.ts` never calls the revocation endpoint. The
capability was built, documented in a comment, and never collected on. The
one-day refresh token — the longest-lived credential in the system —
outlived every sign-out.

Fixed in the C build: logout is now three things (drop local tokens,
best-effort `POST /oauth2/revoke` with `keepalive` so the request survives
the redirect it races, end the Cognito session). What revocation cannot
do is also now stated honestly in the walkthrough: the API's JWT
authorizer verifies offline against cached public keys and never asks
Cognito whether a token is still good, so outstanding access tokens stay
accepted until their ≤1h expiry regardless.

**Why it matters:** Two lessons. First, a comment describing intent is not
the intent — the flag and its caller shipped in the same increment, in
different workspaces, and nothing connected them; only an adversarial pass
that asked "who calls this?" found the gap. Second, the ≤1h acceptance
window is not a bug to fix but the defining trade of stateless
verification — revocation immediacy exchanged for zero-latency auth —
and the honest response is to teach it and pin where it gets revisited
(`docs/decisions/0017`'s BFF gate, before money exists).
