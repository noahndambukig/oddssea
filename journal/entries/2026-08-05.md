# 2026-08-05

## 00:17 — finding — Review of C's plan exposed a B gap: revocation was enabled but never invoked

**What happened:** Round 13 of the Codex review on the Increment C plan
flagged that "sign out → 401" only proves the browser stopped *sending*
credentials. Checking the claim against the shipped Increment B code made
it sharper than the reviewer knew: `infra/lib/constructs/auth.ts` sets
`enableTokenRevocation: true` with the comment "lets logout actually
invalidate the refresh token server-side" — and `logout()` in
`web/src/auth/auth-client.ts` never calls the revocation endpoint. The
capability was built, documented in a comment, and never collected on. The
one-day refresh token — the longest-lived credential in the system —
outlived every sign-out.

Fixed in the C build: logout is now three things (drop local tokens,
best-effort `POST /oauth2/revoke` with `keepalive` so the request survives
the redirect it races, end the Cognito session). What revocation cannot
do is also now stated honestly in the walkthrough: the API's JWT
authorizer verifies offline against cached public keys and never asks
Cognito whether a token is still good, so outstanding access tokens stay
accepted until their ≤1h expiry regardless.

**Why it matters:** Two lessons. First, a comment describing intent is not
the intent — the flag and its caller shipped in the same increment, in
different workspaces, and nothing connected them; only an adversarial pass
that asked "who calls this?" found the gap. Second, the ≤1h acceptance
window is not a bug to fix but the defining trade of stateless
verification — revocation immediacy exchanged for zero-latency auth —
and the honest response is to teach it and pin where it gets revisited
(`docs/decisions/0017`'s BFF gate, before money exists).

**Refs:** `web/src/auth/auth-client.ts` (logout), `infra/README.md`
Part 7 concepts, `.review/replicated-watching-truffle/ledger.md` rounds
10–13

## 01:15 — finding — A review finding was wrong, and only the deployed API could say so

**What happened:** Increment C deployed cleanly (307s; the ordering held —
routes at 12:56:44, cert/domain/mapping/record through 12:59:28, and the
site upload only then, 12:59:29 → 1:01:09, exactly what `api.ready` is
for). Then the first curl against the live API contradicted a plan claim
that had survived a review round and a documentation check.

Codex round 12 asserted that authorizer-generated 401/403 responses carry
no CORS headers, so browser JS would see `TypeError: Failed to fetch`
rather than a status. AWS's own wording supported it — CORS headers are
added "to the response from an integration", and a rejected request never
reaches one. I verified that sentence in the docs, agreed, and rebuilt the
API panel around rendering the block as the demonstration, moving the
numeric checks to curl.

Measured against the deployed API, it is false:

```
$ curl -i https://api.oddssea.xyz/me -H "Origin: https://oddssea.xyz"
HTTP/1.1 401 Unauthorized
access-control-allow-origin: https://oddssea.xyz
```

Correctly absent for an origin outside the allow-list, present for one
inside it. Confirmed in a browser: the panel renders a real `401`. The
advice is genuine but belongs to **REST APIs (v1)**, where gateway
responses need CORS wired by hand; **HTTP APIs (v2)** do it themselves.
Reverted in code and docs; the panel now renders 401/403 with teaching
notes and reserves its catch branch for real network failures.

Also observed, and now taught: signed out, `/me` sends **no** preflight —
there is no `Authorization` header to trigger one. The `OPTIONS` appears
only when signed in. The rule made visible.

**Why it matters:** This is the 2026-08-04 21:15 lesson recurring one
level up. There, a passing typecheck and build did not prove the program
ran. Here, an adversarial reviewer *and* a documentation lookup did not
prove the claim true — a sentence about one case (integration responses)
was read as a statement about another (gateway responses), and the
version distinction that governs it went unnoticed. Both defences were
the strongest available short of running it, and running it took one
curl. **Verify AWS behaviour against the deployed thing, and check which
API generation any advice was written for.**

**Refs:** `web/src/ApiPanel.tsx`, `infra/README.md` Part 7 CORS bullet +
Increment C failure table, `.review/replicated-watching-truffle/ledger.md`
(round 12 #1 CORRECTION)

## 02:20 — milestone — Increment C complete: the token loop closes, and rejection costs nothing

**What happened:** `api.oddssea.xyz` is live and every behavioural check
passes. One Lambda, two routes, verification done by API Gateway's JWT
authorizer against Cognito's published keys. The skeleton the milestone
set out to build — real URL, real login, real token-guarded API — is
finished.

The three-status check, run from a browser against the deployed API with
a throwaway account (created, used, deleted; the real account was never
touched):

| Sent | Status | Meaning |
|---|---|---|
| no token | 401 | the gateway does not know who you are |
| **ID token** | **403** | valid token, wrong kind — no `scope` claim |
| access token | 200 | `sub`, `token_use: access`, and no email |

The 403 is the one that matters. That token is genuine: same issuer, same
signature, and its `aud` is literally the configured audience. It fails
only the `openid` scope requirement — which is the entire reason the
route declares one, and the third leg of a loop whose first two legs
shipped in Increment B.

**The best evidence was an absence.** The Lambda's log group holds
exactly 9 invocations. The three probes above were sent back-to-back;
only **one** appears. Two requests were refused at the front door without
starting compute, without writing a log line, without costing anything.
Across the whole session, ~7 rejected requests produced 0 invocations.
"No Lambda runs for an unauthorised request" stopped being a claim and
became something observed.

Also confirmed: retention is finite (14 days) on the handler's log group,
so the explicit-LogGroup pattern held; cold starts are visible in the
data (151ms init, then 1.5–2ms warm); the 200's body carries **no email**,
because email lives only on the ID token — the two-token split working as
designed rather than as an inconvenience.

**Why it matters:** Three increments, one loop: A proved a URL and a
keyless pipeline, B proved an identity, C proved that identity is worth
something to a service that never talks to the identity provider. The
remaining honest gaps are recorded, not hidden — an access token issued
before logout stays valid until expiry (offline verification's trade),
and the login page is still unstyled by choice.

**Refs:** `infra/lib/constructs/api.ts`, `api/src/handler.ts`,
`infra/README.md` Part 7; the plan at
`.review/replicated-watching-truffle/` (4 rounds, 9 findings, one later
disproven by measurement — see 01:15 above)

## 21:40 — finding — Pass 3 on the data model: eleven issues, four that would have shipped broken

**What happened:** Ran Pass 3 (`spec-workflow.md`) on
`04-technical/data-model.md` before planning the ledger milestone, since
it is the spec that milestone builds against. Eleven findings; all
resolved, and the spec moves draft → agreed (`decisions/0018`).

The four serious ones:

1. **No idempotency anywhere** — the concept appeared in no spec. Rule 2
   promised "one transaction per economic event", which is *atomicity*:
   all-or-nothing for one execution. It says nothing about a request
   arriving twice, and over a mobile network it will, because a client
   that never hears back cannot distinguish a lost request from a lost
   response. The retry would have been a second, perfectly atomic,
   second debit.
2. **No concurrency control on balances or caps** — two concurrent bets
   could both read the same balance and both pass. Not theoretical:
   `game-modes.md` rule 2 keeps all-in a legitimate play with no maximum
   bet, so concurrent all-ins are designed-for. The lottery ticket cap
   has the same hole, and `compliance.md` calls that cap the +EV
   lottery's *compliance boundary* — making it a compliance failure, not
   just an economic one.
3. **`bets` could not represent 2 of the 7 launch games.** Crash has no
   odds at placement (the price is wherever you cash out); blackjack's
   specced double and split turn one bet into a changing stake and two
   hands. One stake and one payout column expresses neither.
4. **Rule 3's roll-logging had a hole exactly where the rolls are** —
   `blackjack_tables`/`roulette_rooms` held "hand/spin state" with no
   roll log, and a six-deck shoe generates a random outcome per card.

Plus: global first-discovery credit — which `dex.md` calls the strongest
flex in the system — had nowhere to live and would have silently moved to
the second finder if the first account were deleted; no ledger kind for
the weekly rotation's direct-purchase route; provenance specified two
different ways within the same file; and **no day boundary defined
anywhere in the docs**, despite streaks, daily/weekly tasks, tip caps,
ticket caps and both lottery draws all depending on one. Days are now
UTC, stated as a rule.

**Why it matters:** Every one of these is cheap as a schema decision and
expensive as a migration, and the timing was luck rather than judgement —
this was run because `data-model` happened to be the next thing on the
critical path, not because anything looked wrong. Nothing built so far is
affected: no API touches a database yet. The pattern to keep is that
Pass 3 has now paid for itself on every spec it has been run on, and the
four remaining drafts (`core-loop`, `tasks`, `game-modes`, `racers`) have
not had it.

Second-order observation worth keeping: **three of the four serious
findings were absences, not errors.** Nothing in the spec was wrong — the
document read as complete because what was missing had no place to be
visibly missing from. Reviewing prose for what it *says* would have
passed it. It only failed when checked against what a production system
must survive.

`docs/04-technical/data-model.md`, `docs/04-technical/hosting.md`
(RDS Proxy)

## 23:05 — finding — The simulations were never seeded, so no economy number could be checked

**What happened:** Pass 3 on the last four drafts (`core-loop`, `tasks`,
`game-modes`, `racers`) turned up sixteen findings. Two matter.

**The committed faucet was overstated.** Pricing `tasks.md`'s structure
with the currency model's own figures gives 550 login + 175 first-bet +
1,575 dailies + 1,100 weeklies = **3,400 Shells/week**. The model claimed
~3,550 and `bankroll.py` used a third value, 500/day (3,500). The casual
profile reconciled to 1,400 **exactly** — and that asymmetry is the whole
tell: one profile was computed from the table and the other was
estimated, and 500/day is what estimation looks like.

**The simulations were unseeded.** No `random.seed` in any of them. Eight
runs of `bankroll.py` spread committed crates/week across **54.0–58.1**
— ±4%, larger than most real design changes. The project's own working
rule is "re-run simulations before changing an economy number, then
update the results of record". That rule could not work: a re-run moved
the numbers more than the change being tested would, so noise and signal
were indistinguishable, and nobody could verify the results-of-record
table against the scripts that supposedly produced it.

Fixed: fixed seed in every script, `bankroll.py` declared to run first,
`crate-game.py`'s crates/week and Pearl income marked as chained
constants copied from it. Re-derived under the seed, the correction moved
every committed figure down 2–3% (crates 53→52, handle ~74k→~72.4k,
Pearls ~4,200→~4,150) and changed no design conclusion — destruction
still lands near 1.0, busts stay at zero, set completion holds its
3-week committed median.

**A methodology error found in passing:** `CLAUDE.md`'s working-rules
block told you to re-run `set-completion.py` and `crate-rates.py` before
changing an economy number. The simulations README marks **both** as
historical, pre-revamp coin-economy scripts producing no current figure —
and omits `bankroll.py` and `crate-game.py`, which produce all of them.
The instruction the project gives itself pointed at the wrong two files.

Also fixed: the login streak capped on day 6 in one file and day 7 in
another; four figures restated in `game-modes.md` (crash cap, pot split,
house match, roster size) in the same file whose Numbers section declares
they live elsewhere; the week had no start day, so `decisions/0018`'s UTC
rule was completed with Monday 00:00 UTC (ISO-8601, every date library's
default); onboarding's free crate was unpriced and homeless, now three
Basic crates — exactly the window `crates.md`'s first-session guarantee
already covers; task completion targets existed nowhere; and
`racers.json` gave Riptide a higher base weight than Sure Thing, whom
`racers.md` called "the favourite", so the odds board would have
contradicted the roster description on most race days.

**Why it matters:** the seeding one is the lesson. Every economy number
in this project traces back to a script, and the whole apparatus —
results of record, "re-run before changing", a decision entry citing
simulated figures — assumed those scripts were reproducible. They were
not, and nothing in the process would ever have surfaced it, because an
unseeded simulation fails by producing *plausible* numbers rather than
wrong ones. The error was invisible precisely because the output always
looked fine.

Second-order: **the faucet error survived because a summary and its
source both looked authoritative.** ~3,550 sat in the numbers-have-one-home
file, which is exactly where you would go to trust it — but it was a
derived figure, and nothing marked it as derived or checked it against
what it summarised. Derived numbers now say so, and say from what.

All five specs are `agreed`. Nothing is drafted any more.

**Refs:** `docs/decisions/0019-pass-3-on-the-game-specs.md`,
`docs/02-economy/simulations/README.md`, `docs/01-game/*`

## 23:50 — decision — RDS Proxy reversed: it would have silently prevented the database from ever pausing

**What happened:** Designing the ledger milestone, the database access path
came down to RDS Proxy (which `decisions/0018` named in `hosting.md` earlier
the same day) versus the RDS Data API. Reading the Aurora auto-pause
documentation — while verifying an unrelated claim about whether minimum
capacity 0 is real — turned up this, under *Situations where Aurora
serverless doesn't auto-pause*:

> "If your Aurora cluster has an associated RDS Proxy, the proxy maintains
> an open connection to each DB instance in the cluster. Thus, any Aurora
> serverless instances in such a cluster won't automatically pause."

And, for the alternative:

> "If you send a request to your cluster through the RDS Data API, Aurora
> resumes the writer instance if it's paused."

So the two decisions were never independent, which is exactly what made it
dangerous. Choosing the proxy would have cancelled scale-to-zero **with no
error and no failed deploy** — just an idle cluster billing every hour,
forever, to solve a connection-exhaustion problem that one developer and
zero players cannot create. The project's entire fixed cost today is one
Route53 hosted zone.

Reversed in `decisions/0020`; `0018` left intact, since decisions are
append-only and its reasoning is correct at volume. `hosting.md` now
specifies the Data API, minimum capacity 0, no VPC-attached compute and no
NAT.

The same paragraph killed a second decision made ten minutes earlier: an
hourly reconciliation job. The troubleshooting section names it precisely —
*"check if any applications that use RDS Data API or Lambda functions are
sending frequent requests so that the instance is never idle long enough to
pause."* A cron that wakes an idle cluster defeats the pause as thoroughly
as a proxy does. Reconciliation became event-driven instead, on the
observation that **drift can only occur when the ledger is written**, so a
scheduled check of an idle system is checking something that provably
cannot have changed.

**Why it matters:** two independently sensible choices — pool your
connections, check your invariants on a schedule — combine into a
configuration that quietly costs money and never reports a problem. Both
are the *textbook* answer at scale and the wrong answer here, and neither
would have surfaced as a failure. The general shape worth remembering:
**a configuration can be wrong without anything breaking**, and the
cheapest place to find that out is the documentation of the feature you are
depending on, read before building rather than after the bill.

Also noted for the plan: a paused cluster resumes in ~15s, or **30+ seconds
after 24 hours asleep** — which for a project idle for days at a time is the
normal case, not the exception. That is a UI state, not a footnote.

**Refs:** `docs/decisions/0020-data-api-over-rds-proxy.md`,
`docs/04-technical/hosting.md`
