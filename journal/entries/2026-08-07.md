**What happened:** Before planning the crates milestone, Noah reversed two

phone; phones remain supported, just not primary. Recorded as

## 01:05 — finding — Reviewing the crates plan found a race in shipped code

**What happened:** The crates milestone plan went through two Codex review
rounds (9 findings, then 3 — all 12 applied). One round-1 finding was not
about the plan at all: the idempotency pattern in the **shipped** 003
functions checks the key *before* taking the player row lock and never
re-checks after, so two concurrent calls with the same key can both miss
the pre-check, serialize on the lock, and the loser errors on the key
insert instead of returning the stored response. `claim_login_task` and
`place_dice_bet` are live in production with this race. Migration 006 will
`CREATE OR REPLACE` both with the re-check under the lock — an additive
migration, not an edit of 003.

**Why it matters:** The race was invisible to every production check the
ledger milestone ran, because those verified sequential replays, not
concurrent ones. It surfaced only because a *new* plan restated the
pattern and a reviewer asked what happens between the pre-check and the
lock. The general lesson: an idempotency check done outside the lock is
advisory; only the re-check inside it is load-bearing. The adversarial
checklist now includes a genuinely concurrent same-key test, which the
ledger's never did.

**Refs:** `api/migrations/003_functions.sql`,
`.review/replicated-watching-truffle/ledger.md`

## 01:05 — decision — The sim of record outranks spec prose (keystone edge)

**What happened:** Codex flagged that two Legendary rolls in the first four
set-crate opens produce a duplicate keystone, "violating" crates.md's
"first four pulls are guaranteed distinct." Resolution went the other way:
`crate-game.py` redirects only non-keystone pieces (`if piece != 5`), the
published set-completion numbers were generated with that exact semantics,
and the guarantee's own rationale targets triple-common misery, not double
jackpots. The runtime will match the sim — keystone exempt, the ~0.24%
duplicate recorded like any pull — and crates.md's prose gets clarified to
say so.

**Why it matters:** First explicit precedence ruling between a spec's
prose and its simulation of record. "Fixing" the runtime to match the
prose would have quietly made the set chase cheaper than the simulated
economy — a number changing without its home changing. When prose and sim
disagree, the sim that produced the results of record wins, and the prose
is corrected as documentation, not the other way round.

**Refs:** `docs/02-economy/simulations/crate-game.py`,
`docs/03-cosmetics/crates.md`

## 02:55 — finding — The adversarial suite caught a privilege hole the harness could not

**What happened:** Crates deployed (006 applied cleanly, both routes live)
and the production adversarial suite ran on a dedicated test account:
36 of 37 checks passed — including the concurrent same-key race
returning one `crate_opens` row with identical stored responses (the 003
retrofit working live), the drought firing on the open after exactly ten
misses, and four set opens yielding four distinct pieces. The one failure
was the deliverable working as intended: `crate_open_locked()` as
`oddssea_app` returned `candidates missing tier` — the function RAN. The
internal helper that skips idempotency, attestation, the starter gate and
the balance check was executable by the app role. `pg_proc.proacl`
confirmed it: NULL (built-in default — PUBLIC may execute), and 006's
explicit grants had materialised a `=X` PUBLIC entry onto `open_crate`
and `claim_starter_crates` too.

**Why it matters:** The cause is a silent no-op in shipped 004:
`ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS
FROM PUBLIC` cannot do what its name says — per-schema default ACLs are
*added* to the global defaults and can only subtract privileges a
per-schema grant default added, never PostgreSQL's built-in
PUBLIC-execute. The belief that new functions "default to no access" held
since 004 shipped and nothing ever tested it, because every function
created between then and now was one we *meant* to grant. It took a check
that expected `permission denied` to notice. Migration 007 revokes PUBLIC
from the three 006 functions and issues the *global*
`ALTER DEFAULT PRIVILEGES` that actually works. Two lessons: the 003
functions were only ever safe because the blanket `REVOKE ON ALL
FUNCTIONS` ran after them, not because of the default-privileges line;
and `CREATE OR REPLACE` preserving ACLs is what kept the 006 retrofits
clean — the same property that made the retrofit additive made it safe.

**Refs:** `api/migrations/007_revoke_public_execute.sql`,
`infra/README.md` Part 9 failure modes

## 03:09 — decision — The tasks milestone planned: partial rollout of a priced structure

**What happened:** The faucet milestone was planned and reviewed (three
Codex rounds: 5 → 5 → 3 findings, all 13 applied). Noah's four scope
calls: draw 2 challenges/day from the honestly buildable pool rather than
pad it; a shared global draw derived from the UTC date; the weekly
volume task at 100 bets with its 4-games clause waived until the roster
exists; a 3-step tour now (intro → starter crates → first bet). Committed
interim faucet ≈ 2,575/week against the full-spec 3,400 — no number
changes anywhere, because partial rollout of a priced structure is not a
spec change. One derivation fell out rather than being chosen: a "daily
set" must mean login + first bet + ≥2 challenges, because
currency-model.md's own casual arithmetic (4 × [50+25+150] + 500 =
1,400) is inconsistent with anything stricter.

**Why it matters:** Two things worth keeping. First, the review caught
its own revision: round 1 added draw-membership validation, and round
2's only High was that this check would have rejected `first_bet` — the
one daily task deliberately outside the draw. A fix that adds a gate
must re-ask which traffic the gate was never meant to stop. Second, an
explicit waiver was recorded rather than discovered: the spec's
bust-proof rule leans on zero-Shell tasks (races, closets) that are
deferred with their features, so until they land a post-login bust has
no same-day recovery. Recording the gap in `decisions/0024` beats
someone finding it in a playtest and calling it a bug.

**Refs:** `.review/replicated-watching-truffle/ledger.md` (13
dispositions), `docs/01-game/tasks.md`,

## 04:19 — decision — Closet planned: expand/contract, learned twice in one review

**What happened:** The closet/equipping milestone planned (equip-only,
private — the public closet defers to the flex milestone; the tour's
equip step inserts as step 3 per spec). Two Codex rounds, 7 findings,
all applied. The instructive pair: round 1 flagged that migration 009's
chain rewire would land minutes before the handler that can satisfy it,
so the plan split it expand/contract — 009 adds, 010 rewires in a second
same-branch deploy. Round 2 then caught that the FIX was still wrong:
after 010, an app-stack rollback lands on a handler with no closet route
and no `tour:equip` in its valid set — the contracted chain strands new
players anyway. 010 moved out of the milestone entirely; it ships as the
first commit of the NEXT milestone's branch, the earliest point where
the rollback target itself contains the closet code. Interim: the tour's
order is UI-presented but SQL-permissive for one milestone gap, recorded
in `decisions/0025` as a forward obligation.

**Why it matters:** Expand/contract is not "two migrations instead of
one" — it is "the contract waits until rolling back is safe," and the
window is measured in deploys you might return to, not minutes between
stacks. Second lesson from the same review: a task that rewards an EVENT
must not read current state — equip evidence became a COALESCE'd
timestamp on players, because equip-then-unequip-before-claim would
otherwise erase the credit in both the SQL condition and the UI flag
(which round 2 also caught still reading the wrong source).

**Refs:** `.review/replicated-watching-truffle/ledger.md` (7
dispositions), `docs/04-technical/data-model.md` (loadouts)

## 13:15 — decision — The pause is over: always-on database on credits

**What happened:** Noah ended the scale-to-zero era: minimum capacity
0 → 0.5, auto-pause removed (`decisions/0026`). Dev runs on AWS credits
(~$44/month at the floor), so the cash cost is ~zero; the payoff is no
cold starts and — the real motive — the shared-round games (crash,
roulette, lottery) get to choose their design freely, because a ticker no
longer silently sabotages a pause. The decision followed a three-turn
evaluation: always-on Aurora at $44 vs Supabase free tier (always-on at
$0 but with a manual-resume pause after an idle week, and a one-session
migration) vs staying scale-to-zero with time-indexed lazy rounds. The
resolution is a sequence, not a pick: **credits pay for Aurora always-on
through dev; the plan of record migrates off Aurora before launch.**

**Why it matters:** The migration-cost question got a structural answer
worth keeping: deferring the database move does NOT grow its cost,
because every migration is plain Postgres, all access flows through
db.ts's two functions, and each milestone's adversarial suite is the
migration's re-verification harness — the cost inflates only if the move
happens after real players exist. 0020's choices survive their own
rationale: the Data API, no VPC, no proxy were picked FOR auto-pause and
kept for simplicity. And the client's waking machinery stays — proven
code covering restarts costs nothing to keep.

**Refs:** `docs/decisions/0026-always-on-database-on-credits.md`,
`docs/04-technical/hosting.md`, `infra/lib/data-stack.ts`
