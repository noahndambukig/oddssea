## 00:15 — decision — Laptop-first, and mechanics before art

**What happened:** Before planning the crates milestone, Noah reversed two
presentation postures. First, phone-first design is dropped: `platform.md`
had "designed for a ~375px portrait phone first and expanded for desktop —
never the reverse" as a hard gate, and the site is now designed for the
laptop with phone-usable as the check. Second, the UI stays deliberately
barebones — buttons, text, lists — until the game's mechanics are complete;
art becomes its own phase afterwards rather than a per-milestone tax.

**Why it matters:** Phone-first bought quality for a mobile audience the
project does not yet have, at a second-layout-pass cost on every screen.
And sequencing art after mechanics matches what the ledger milestone
demonstrated — all ten of its execution-found bugs were mechanical, none
visual — while turning the ~220–380h art track into a single phase against
a stable game. The 8-animated-avatar load test still runs on a low-end
phone; phones remain supported, just not primary. Recorded as
`decisions/0022`; `platform.md` rewritten, status unchanged.

**Refs:** `docs/decisions/0022-laptop-first-mechanics-before-art.md`,
`docs/04-technical/platform.md`

## 01:05 — finding — Reviewing the crates plan found a race in shipped code

**What happened:** The crates milestone plan went through two Codex review
rounds (9 findings, then 3 — all 12 applied). One round-1 finding was not
about the plan at all: the idempotency pattern in the **shipped** 003
functions checks the key *before* taking the player row lock and never
re-checks after, so two concurrent calls with the same key can both miss
the pre-check, serialize on the lock, and the loser errors on the key
insert instead of returning the stored response. `claim_login_task` and
`place_dice_bet` are live in production with this race. Migration 006 will
`CREATE OR REPLACE` both with the re-check under the lock — an additive
migration, not an edit of 003.

**Why it matters:** The race was invisible to every production check the
ledger milestone ran, because those verified sequential replays, not
concurrent ones. It surfaced only because a *new* plan restated the
pattern and a reviewer asked what happens between the pre-check and the
lock. The general lesson: an idempotency check done outside the lock is
advisory; only the re-check inside it is load-bearing. The adversarial
checklist now includes a genuinely concurrent same-key test, which the
ledger's never did.

**Refs:** `api/migrations/003_functions.sql`,
`.review/replicated-watching-truffle/ledger.md`

## 01:05 — decision — The sim of record outranks spec prose (keystone edge)

**What happened:** Codex flagged that two Legendary rolls in the first four
set-crate opens produce a duplicate keystone, "violating" crates.md's
"first four pulls are guaranteed distinct." Resolution went the other way:
`crate-game.py` redirects only non-keystone pieces (`if piece != 5`), the
published set-completion numbers were generated with that exact semantics,
and the guarantee's own rationale targets triple-common misery, not double
jackpots. The runtime will match the sim — keystone exempt, the ~0.24%
duplicate recorded like any pull — and crates.md's prose gets clarified to
say so.

**Why it matters:** First explicit precedence ruling between a spec's
prose and its simulation of record. "Fixing" the runtime to match the
prose would have quietly made the set chase cheaper than the simulated
economy — a number changing without its home changing. When prose and sim
disagree, the sim that produced the results of record wins, and the prose
is corrected as documentation, not the other way round.

**Refs:** `docs/02-economy/simulations/crate-game.py`,
`docs/03-cosmetics/crates.md`

## 02:10 — milestone — Crates built: the selection harness passed 32/32 first run

**What happened:** The crates milestone built end to end in one pass:
catalogue module (66+66 items derived from the content JSONs, validated at
cold start), pre-roll module (CSPRNG tier roll, per-tier candidates,
Fisher-Yates set permutation), migration 006 (items, dex_entries,
crate_opens, pity_counters, one_time_claims, two indexes, `open_crate` +
`claim_starter_crates`, and the CREATE OR REPLACE retrofit of the 003
race), three routes, and the barebones panel. Before anything else was
built on top, a scratch harness ran the selection logic: catalogue counts,
the keystone wall, 10⁶ tier rolls per crate kind within 0.5% of the
published rates, and all four pity counters driven to their exact
boundaries — fires ON the 200th/40th/100th open, drought on the 11th.
All 32 checks passed on the first run. The real splitter from migrate.ts
was also run against 006 (19 statements, dollar quotes balanced) — its
top-level comments contain semicolons, the exact input class that broke
the splitter's first version.

**Why it matters:** The clean first run is the review process working,
not luck: the boundary semantics the harness checks (increment-then-check,
drought-as-exception, keystone exemption) were all settled — twice
corrected — during the two Codex rounds before any code existed. Compare
the ledger milestone, where the plan was reviewed nine rounds and the
build still surfaced ten execution bugs, all in territory the plan never
mapped (shells, casts, response parsing). The crates build's risky
territory WAS the mapped territory this time. Production adversarial
checks (concurrency, the SQL side of pity) remain — the harness proves
the Node half and the semantics, not the deployed transaction.
Completion bonuses reached the runtime by mirroring currency-model.md's
two figures into drop-tables.json (1.1.0, additive — the price_pearls
precedent), keeping numbers out of code.
